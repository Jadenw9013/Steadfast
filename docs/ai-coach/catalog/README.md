# USDA FoodData Central (FDC) food catalog and RD curation workflow

This directory documents the ingestion pipeline, allowlist governance, and clinical curation workflow for the Steadfast AI Coach food catalog (ticket T-2035).

> **The data files are outputs of a real operator run, never hand-written, and never hand-edited afterwards.**
> The first version of this ticket shipped a hand-authored 260-item allowlist and catalog whose FDC ids were a
> contiguous counter (171001..171260) and whose "recorded" fixtures described foods that do not exist in USDA,
> while asserting a CC0 attribution and a retrieval date for every one. All of it was deleted
> (`board/evidence/T-2035.md`) and regenerated by a real run against the live API on 2026-09-26, whose output is
> committed together with its logs (`board/evidence/T-2035-real-run.md`). A record carrying a source's name,
> attribution or retrieval date is a claim that it was retrieved from that source; if it was not, it must not
> exist. When you cannot make the run, the answer is to stop, not to write plausible rows.
>
> The same rule applies **after** the run. `data/ai-coach/catalog/fdc-allowlist.v1.json` and
> `lib/ai-coach/artifacts/drafts/food-catalog-fdc.draft-unsigned.v1.json` are run output: if a field in them is
> wrong, the fix is in the code plus a re-run, never an edit to the file. The first real run hand-set 48 entries
> to `reviewState: "STRUCK"` with a `reviewerNote` saying USDA did not carry their macronutrients. USDA did carry
> them; the tool's nutrient lookup was too narrow (review r2 MB-1). A wrong statement about the source was
> handed to the reviewer as if the reviewer had made it, in a file the section above calls run output. Both the
> states and the notes were reverted and the lookup widened.

---

## 1. Overview and architecture

To satisfy G02 without asking a Registered Dietitian to author hundreds of food records from nothing, Steadfast uses an offline, deterministic ingestion pipeline over the USDA FoodData Central API.

| Component | Path | Checked in? |
|---|---|---|
| Coverage plan | `data/ai-coach/catalog/fdc-coverage-plan.v1.json` | engineer-authored; category ids, per-category target counts and search terms |
| Allowlist | `data/ai-coach/catalog/fdc-allowlist.v1.json` | **output of `--propose`** against the live API. `categoryId`, `patternTags` and `triageFlags` on each entry are machine-derived proposals; see §2.2 |
| Source exclusions | `data/ai-coach/catalog/fdc-source-exclusions.v1.json` | **written by `--ingest`** when a record cannot be mapped. Machine-written only; see §2.1 |
| Draft catalog artifact | `lib/ai-coach/artifacts/drafts/food-catalog-fdc.draft-unsigned.v1.json` | **output of `--ingest`** against the live API |
| Offline CLI | `scripts/ai-coach-ingest-fdc.ts` | yes. Never executes in CI or at runtime; requires an operator-supplied `FDC_API_KEY` |
| Pure mapping modules | `lib/ai-coach/catalog/fdc/*.ts` | yes. No network, no fs, no `process.env` |

The catalog size is whatever the coverage plan's `targetCount` values sum to and whatever the run actually returns — the two differ whenever a search term returns fewer usable candidates than its target, and the run output is the authority. Do not restate a fixed item count here or in a ticket log; the previous version of this file said "250 items total" while the shipped allowlist held 260, and both numbers were invented.

`loadDraftUnsignedFoodCatalog()` reads the artifact at call time and throws a named error while it does not exist, so a missing run is a loud failure rather than a silently empty catalog. It also refuses to load at all when `NODE_ENV === "production"`.

## 2. RD review and curation workflow

The allowlist starts at `curationState: "ENGINEER_DRAFT"` with every entry at `reviewState: "PROPOSED"`. Review proceeds category by category (`categoryId` groups the entries; the coverage plan defines which ids exist and `--ingest` rejects an allowlist naming any other).

For each entry the RD either:
- sets `reviewState: "ACCEPTED"` — a canonical, generic food suitable for coaching plans; or
- sets `reviewState: "STRUCK"` — excluded (duplicate, ambiguous, or unsuitable), with a `reviewerNote`.

Then update `curationState` to `"REVIEWER_IN_PROGRESS"` while working and `"REVIEWER_COMPLETE"` when every category has been reviewed.

> [!IMPORTANT]
> Engineering never marks an entry `ACCEPTED`. An allowlist in `ENGINEER_DRAFT` contains zero `ACCEPTED` entries, and a unit test asserts it over the checked-in file.

> [!IMPORTANT]
> **`reviewState` has exactly one writer: the RD, by hand, in review.** `STRUCK` means *the reviewer excluded
> this food*. It is not a place to record that the pipeline could not process a record, and no agent, script or
> engineer may set it — not to unblock a run, not to explain a failure. Writing a tool failure into `STRUCK`
> gives the field two meanings with opposite owners and puts a sentence the reviewer never wrote next to their
> name. It happened once, on 2026-09-26, and was reverted. When the tool cannot map a record, it writes to its
> own file instead — §2.1.

## 2.1 Source exclusions: the tool's channel, which is not the reviewer's

`data/ai-coach/catalog/fdc-source-exclusions.v1.json` records the entries `--ingest` could not map.

**It records a source limitation. It never records a review decision. The two must never be conflated.**
An entry here is still `reviewState: "PROPOSED"`: the RD may still accept it or strike it, and a later run
picks it up if the source improves. `STRUCK` remains the reviewer's word for "I excluded this food", and this
file remains the tool's word for "the record does not carry what the catalog needs". They answer different
questions and they have different authors.

The file is machine-written and hand-written never. `writtenBy` is the literal `"INGESTION_TOOL"` and `notice`
is a frozen string, so a file claiming any other author does not parse. Every `reason` is the mapper's own
message, verbatim — nobody paraphrases what the source did or did not supply, because that paraphrase is what
went wrong: 48 reviewer notes said "the USDA source record does not carry the macronutrients this catalog
requires" about records that carried all of them.

Each entry holds the `fdcId`, the allowlist entry's `canonicalName`, the verbatim `reason`, the mapper's
`errorCodes` and the `runDate`. Entries are sorted by `fdcId`, so a run that changes nothing produces no diff.
The file is checked in so the RD can read what the tool dropped and why without running anything.

**How a run behaves.** `--ingest` is a two-pass operation the first time an entry fails:

1. Every unmappable entry is logged, the complete exclusion set is written to the file, and the run **exits
   non-zero having written no catalog** — exactly as it did before this file existed.
2. Re-running with the file present skips those `fdcId`s, says how many were skipped and from which file, and
   writes the catalog.

```bash
FDC_API_KEY=... pnpm ai-coach:fdc:ingest -- \
  --allowlist data/ai-coach/catalog/fdc-allowlist.v1.json \
  --out lib/ai-coach/artifacts/drafts/food-catalog-fdc.draft-unsigned.v1.json \
  [--source-exclusions data/ai-coach/catalog/fdc-source-exclusions.v1.json]
```

It is fail-closed in both directions:

- An unmappable entry that is **not** in the file still aborts the run. Nothing is skipped silently.
- An entry that **is** in the file but now maps successfully **also** aborts the run. The file's claim is that
  the source cannot supply the macros; if it can, the claim is stale and a usable food would be dropped on it.
  Remove the entry and re-run. Excluded entries are therefore still fetched and still mapped — that re-check is
  the only way staleness can be noticed.
- A fetch failure is **not** a source limitation. A 404 or a timeout says nothing about what the record
  contains, so it is never written to this file; it aborts the run on its own.
- An unreadable exclusions file aborts rather than being treated as "no exclusions".

**When an entry lands here, the first question is whether the tool is wrong.** The 48 entries of 2026-09-26
were a lookup that read FDC nutrient *ids* where the record carries nutrient *numbers*. Fix the mapper first;
this file is for records that genuinely do not carry the data — oils with only a lipid profile, zero-moisture
research samples, a spaghetti record with 19 nutrient rows and no macro among them — and for records whose
value the catalog cannot represent honestly, such as the negative by-difference carbohydrates in §4.

Re-run ingestion after review:

```bash
FDC_API_KEY="$(cat ~/.steadfast-fdc-key)" pnpm ai-coach:fdc:ingest -- \
  --allowlist data/ai-coach/catalog/fdc-allowlist.v1.json \
  --out lib/ai-coach/artifacts/drafts/food-catalog-fdc.draft-unsigned.v1.json
```

`--ingest` re-verifies the allowlist's `coveragePlanDigest` against the coverage plan before fetching anything, so an allowlist generated against an older plan stops the run instead of ingesting silently. `STRUCK` entries are logged and skipped; they are never fetched and never reach the artifact. Per-entry acceptance lives in the allowlist and nowhere else — the review metadata has no acceptance array, so there is one writer and one truth.

The artifact is `DRAFT_UNSIGNED` whatever the run returns. Real source data is not a substitute for the RD signature (G01); it is the precondition for asking for one.

## 2.2 Machine-derived curation fields: `categoryId`, `patternTags`, `triageFlags` (T-2016)

**Everything in this section is engineer-proposed scaffolding until the RD review.** It is written by
`--propose` from the record's own USDA `foodCategory` and its own description, it is recomputed from scratch on
every run, and none of it is a clinical judgment. `reviewState` and `reviewerNote` stay the reviewer's, exactly
as in §2.1: the tool has its own fields and never writes theirs.

Three fields used to be engineer-set constants presented as facts about the food (review r2 FU-3):

- **`singleIngredientWholeFood` is deleted.** It was `true` on 245 of 245 entries, including `TACO BELL,
  Nachos`, `Candies, nougat, with almonds` and `Oil, industrial, canola (partially hydrogenated) oil for deep
  fat frying`. The allergen rule that read it was removed in the T-2035 repair, so it was an unverified claim
  with no reader. The entry schema is `.strict()`, so an allowlist still carrying the field does not parse.
- **`categoryId`** was whichever coverage-plan *search term* returned the record, so `TACO BELL, Nachos` was
  `VEGETABLES`, `Croissants, apple` was `FRUITS` and `APPLEBEE'S, Double Crunch Shrimp` was `SEAFOOD`.
- **`patternTags`** was `["OMNIVORE"]` on every entry, so any pattern-filtered read for a `VEGAN`,
  `LACTO_OVO_VEGETARIAN` or `PESCATARIAN` client returned the empty set.

### How `patternTags` is derived, and that it fails closed

`lib/ai-coach/catalog/fdc/curation.ts` maps the record's own USDA food group onto the four patterns:

| USDA food group | Patterns the group establishes (before the description narrows them, below) |
|---|---|
| Vegetables and Vegetable Products, Fruits and Fruit Juices, Cereal Grains and Pasta, Legumes and Legume Products, Nut and Seed Products | all four |
| Dairy and Egg Products | `LACTO_OVO_VEGETARIAN`, `PESCATARIAN`, `OMNIVORE` |
| Finfish and Shellfish Products | `PESCATARIAN`, `OMNIVORE` |
| Poultry, Beef, Pork, Lamb/Veal/Game, Sausages and Luncheon Meats | `OMNIVORE` |
| **everything else, including every unrecognised string and a record with no category** | `OMNIVORE` |

**It fails closed to omnivore-only whenever the category does not unambiguously establish the set** — every
mixed dish, restaurant item, candy, baby food, soup and beverage group, and every category string the table
does not recognise. Omnivore-only excludes the food from the three restricted patterns, which is the safe
direction: a vegan client not offered broccoli gets a poorer catalog, a vegan client offered chicken gets a
broken promise. `patternTagsBasis` records which of the three happened — derived, narrowed, or fallen back — so an entry
derived from an unambiguous category is distinguishable from one that fell back — both read `["OMNIVORE"]` for a beef record and a candy record, and
only the basis tells them apart.

**Why reading `foodCategory` here is not a reintroduction of review r2 MB-2.** That finding removed the
category from the *allergen* rule, where it declared crustacean shellfish present in all 14 finfish and wheat
present in quinoa and rice. An allergen declaration is a statement about a food's ingredients and processing,
which a food group does not establish. Which eating patterns a food belongs to is a question of the food's
*identity*, and its USDA food group is exactly a statement of identity. The two live in different modules, the
description is never read for pattern tags, and a unit test pins that no curation field on an entry changes any
allergen fact.

**`"Fats and Oils"` is deliberately not a plant group.** USDA's Fats and Oils group holds lard, tallow, butter
oil, the fish oils, margarine and mayonnaise next to the plant oils — `Mayonnaise, reduced fat, with olive oil`
and three `Fish oil, …` records are in the current allowlist — so a plant tag set derived from it would offer a
vegan client cod liver oil. Plant oils therefore carry omnivore-only until the RD widens them.

### The description narrows, and may never widen

A plant-named USDA group still contains prepared items that are not plant-only: `Spinach souffle` is a real
member of "Vegetables and Vegetable Products" and is made of eggs and cheese, and
`Pasta mix, classic beef, unprepared` may well sit in "Cereal Grains and Pasta". The category alone would ship
both tagged `VEGAN`.

So after the category has spoken, the record's own description can **remove** patterns from the set, and can
never add one. The direction is the whole safety argument: inferring a property *from* a name is what produced
the allergen defects in §3 (`Beverages, rice milk` read `MILK: PRESENT`), but declining to assert a property
because of a name adds no claim at all. The result is always a subset of what the category produced, so the
worst case is a food the catalog does not offer, never a food it offers falsely. A unit test asserts that subset
property over every indicator term in every category.

Each indicator carries the patterns it still permits, rather than resetting everything to omnivore-only. A
blanket reset would delete exactly the foods each restricted pattern is defined by: every dairy description says
"cheese" or "yogurt" and every seafood description says "fish" or "shrimp", so it would strip
`LACTO_OVO_VEGETARIAN` from all 33 dairy and egg entries and `PESCATARIAN` from all 25 seafood entries — a
pescatarian catalog with no fish in it. For a plant-category record the intersection gives the intended answer
anyway: a flesh term (`beef`, `chicken`, `gelatin`, `broth`) leaves omnivore-only, a fish term leaves
pescatarian, and a dairy, egg or preparation term (`cheese`, `cream`, `custard`, `souffle`, `gratin`,
`scalloped`, `breaded`, `honey`) removes `VEGAN`.

`patternTagsBasis: "NARROWED_BY_DESCRIPTION"` marks it and `patternTagsNarrowedBy` lists the terms that did it,
so an RD who disagrees can find every narrowed entry and widen it. A match that removes nothing is not recorded
as a narrowing.

`butter` is deliberately not an indicator and `creamy` cannot match one. Both are food forms — `Almond butter,
creamy`, `Peanut butter, creamy`, `Nuts, cashew butter` and `Fruit butters, apple` are all in the current
allowlist — and this is the same trap the allergen term list fell into once and now documents in §3. Real butter
sits in "Dairy and Egg Products", which already excludes `VEGAN`.

**It is a heuristic, it will miss things, and it is not a substitute for the RD review.** A creamed vegetable
under a spelling the list does not carry still ships with plant tags. It is blunt in the safe direction too:
`Fish oil, cod liver` matches `liver` and loses `PESCATARIAN`, which the RD may want back. What it closes is the
set of cases where the pipeline would otherwise assert something false with confidence, which is the only part
that is ours to close. Measured over the 245 committed descriptions against their coverage-plan groups, it
changes 4 entries and costs 3 of them their `VEGAN` tag.

A reviewer who sets their own tags sets `patternTagsBasis: "REVIEWER_SET"`. That basis exists because the
allowlist schema **re-derives** any entry claiming `SOURCE_FOOD_CATEGORY` or `NARROWED_BY_DESCRIPTION` from its
own recorded inputs — `sourceFoodCategory` and `canonicalName` — and refuses the file when the two disagree: a
stated basis must be reproducible from the stated input, so a hand-widened tag set cannot masquerade as
something the source said.

### How `categoryId` is derived

The same module maps the record's food group onto the coverage plan's ten ids, preferring it over the search
term. "Baked Products" and "Breakfast Cereals" map to `GRAINS_STARCHES`, which is what moves `Croissants,
apple` out of `FRUITS`. "Dairy and Egg Products" cannot choose between `DAIRY` and `EGGS`, so the plan's value
is kept and `categoryIdBasis` says `SOURCE_FOOD_CATEGORY_AMBIGUOUS_PLAN_KEPT`. **Where no confident mapping
exists the plan-assigned value is kept unchanged and the entry is flagged** rather than guessed at.

### Triage flags

`triageFlags` is machine-written and recomputed every run. It exists because `--propose` takes search hits
unfiltered, so roughly 29 of 245 entries are restaurant, candy, baby food or industrial-oil records (review r2
FU-5): nothing unsafe, because everything is `PROPOSED`, but it costs the RD time and skews any "the catalog has
N foods" claim. A flag names what the tool detected in the description or the category —
`DESCRIPTION_CARRIES_AN_ALL_CAPS_BRAND_TOKEN`, `DESCRIPTION_NAMES_A_BABY_OR_TODDLER_FOOD`,
`DESCRIPTION_NAMES_A_CONFECTIONERY_OR_DESSERT`, `DESCRIPTION_NAMES_AN_INDUSTRIAL_OR_HYDROGENATED_OIL` and the
rest — so a flagged group can be struck in bulk instead of read row by row.

> [!IMPORTANT]
> **Flags are the tool's; `reviewState` is the reviewer's; the two never mix.** A flag excludes nothing and
> decides nothing. Striking a flagged entry is the RD's act and the one legitimate use of `STRUCK`.
> **The absence of a flag is not a claim either**: this is keyword triage over USDA description text, not a
> classifier. It misses things (`Fruit butters, apple`) and it will flag a food the RD may want to keep
> (`Rice, white, steamed, Chinese restaurant`). Never read an empty `triageFlags` as "the tool judged this a
> good candidate".

### For consumers (T-2036)

- **No consumer may read an empty pattern-filtered result as "no foods exist".** It means no food in the
  catalog carries that tag, which today can be a derivation that failed closed rather than a fact about food.
- **T-2036 must degrade rather than disappear on an empty filter result** — show the unfiltered catalog behind
  an explicit notice, or an explicit empty state that says the catalog has nothing tagged for this pattern yet.
  A screen that vanishes is forbidden by `board/strategy/release-safety.md`, and it is the reason this ticket
  exists. There is no such consumer today: nothing in `lib/` or `app/` reads `patternTags`.
- `categoryId`, `patternTags` and `triageFlags` are all engineer proposals until `curationState` reaches
  `REVIEWER_COMPLETE`. Do not present any of them to a client as a dietary classification.

## 3. Allergen tri-state rules and fail-closed safety

Allergen facts use T-2002's nine frozen categories: `MILK, EGG, FISH, CRUSTACEAN_SHELLFISH, TREE_NUT, PEANUT, WHEAT, SOYBEAN, SESAME`.

**The rule: `VERIFIED_ABSENT` requires positive evidence in the source record that the allergen is absent. Everything else is `UNKNOWN`.**

- **`PRESENT`** — the record's own identity names the allergen (the curated canonical name, the USDA description or a curated synonym), or the allowlist entry declares the food *is* that allergen. `basis: "SOURCE_RECORD_IDENTITY"`.
  - **The USDA `foodCategory` is deliberately not scanned**, which departs from the frozen spec. Measured over
    the first real run, 42 of 130 `PRESENT` facts came only from the category string and none of them were
    true: all 14 finfish read `CRUSTACEAN_SHELLFISH` from "Finfish and Shellfish Products", quinoa and white
    rice read `WHEAT` from "Cereal Grains and Pasta", cheddar read `EGG` and egg white read `MILK` from "Dairy
    and Egg Products" (review r2 MB-2). Over-declaring is not the safe direction: `UNKNOWN` already fails
    closed, so a false `PRESENT` excludes nothing that `UNKNOWN` would not have, and what it does buy is a
    document the RD is asked to sign that says cod contains crustacean shellfish. `PRESENT` must be true.
  - Terms are matched on whole words with **generated plural forms** (`almond` matches `Nuts, almonds`,
    `anchovy` matches `anchovies`) and possessives. Listing only singulars used to lose the commonest USDA
    spelling: `Nuts, almonds` and three walnut records shipped declaring no tree nut at all (review r2 MB-3).
    Add terms in the singular only; a unit test asserts every term in all nine lists matches its own plural.
  - **A term names the allergen substance itself, never a food form that can be made from something else.**
    `butter` is a form (cashew butter, apple butter); `flour` is a form (rice flour, chickpea flour); so are
    `bread`, `pasta`, `bran`, `custard` and `mayonnaise`. All are removed. In the first real run they produced
    `WHEAT: PRESENT` on `Chickpea flour (besan)`, four rice-flour records and
    `Pasta, gluten-free, corn flour and quinoa flour`, and `MILK: PRESENT` on both `Nuts, cashew butter`
    records and `Fruit butters, apple`. What stays is substances and fractions: `cream`, `cheese`, `yogurt`,
    `whey`, `casein`, `lactose`, `buttermilk`, `butterfat`, `ghee`, `dairy`; `semolina`, `durum`, `spelt`,
    `kamut`, `farro`, `bulgur`, `couscous`, `gluten`, `seitan`; every fish, crustacean, tree nut and peanut
    entry. `tofu`, `tempeh`, `miso` and `tahini` stay because the unqualified name has no non-allergen
    production base — a chickpea tofu is always written "chickpea tofu".
  - The coverage loss is the correct cost. `Pasta, dry, enriched` and `Butter, salted` become `UNKNOWN`
    instead of `PRESENT`, and `UNKNOWN` excludes a client who declared the allergen exactly as `PRESENT`
    does. Nothing is made less safe, and every positive claim left in the document is one the reviewer can
    trust. `Bread, whole-wheat, commercially prepared` still reads `WHEAT` through `wheat`; a unit test pins
    that, and pins the gluten-free pasta and the chickpea flour as *not* wheat.
  - **`<term>-free` is a negation, not a mention.** `Pasta, gluten-free, …` used to read `WHEAT: PRESENT`
    through `gluten` — a food whose own name says it does not contain the allergen, declared as containing
    it. The matcher refuses `<term>-free` and `<term> free`. The result is `UNKNOWN`, never
    `VERIFIED_ABSENT`: a label phrase in a USDA description is not the positive evidence of absence this
    module requires, so the food still fails closed for a client who declared it. Narrow on purpose —
    `milk-fat free` is not `milk free`, so `Milk dessert, frozen, milk-fat free` still reads `MILK`.
  - **Known residue, not fixed here.** A non-dairy analogue named after the dairy product still reads
    `MILK: PRESENT`: `Beverages, rice milk`, `Tofu yogurt`, and
    `Oil, industrial, coconut … for ice cream coatings`. These are compound qualifiers rather than food
    forms, so the rule above does not reach them and a negative-qualifier mechanism would be a new design.
    `coconut` is deliberately absent from `TREE_NUT` although the FDA classifies it as one; that is an RD
    call, and `UNKNOWN` blocks a tree-nut-allergic client either way.
- **`UNKNOWN`** — everything else. `basis: "NONE"`, `verifiedAt: null`.
- **`VERIFIED_ABSENT`** — not emitted by ingestion at all, and the emitted type says so rather than a comment saying so.

Why there is no absence branch, from the record structure itself (probed live 2026-09-26):

- A **Foundation** record has 16 top-level keys (`dataType, description, fdcId, foodAttributes, foodCategory, foodClass, foodComponents, foodNutrients, foodPortions, footnote, inputFoods, isHistoricalReference, ndbNumber, nutrientConversionFactors, publicationDate, scientificName`). There is no `ingredients` field, no "contains" declaration, no allergen field.
- An **SR Legacy** record is the same minus `inputFoods`/`foodComponents`, and its descriptions include commercially prepared foods whose real ingredient statements routinely include soybean oil, milk solids and sesame.
- A **Branded** record is the only data type carrying an `ingredients` statement, because US labelling law requires one. v1 does not accept Branded records and does not parse ingredient statements.

Absence of an ingredient list is not evidence of absence. A category label is not evidence of absence. An empty `inputFoods` array is not evidence of absence. The `singleIngredientWholeFood` flag was not in the record at all, and T-2016 deleted the field (§2.2). A food group *is* evidence of the food's identity, which is why §2.2 may read it for eating patterns and this section may not read it for an allergen declaration. The deleted catalog inferred absence from exactly those signals and produced 2,119 `VERIFIED_ABSENT` facts out of 2,340 — including sesame and soy "absent" from sourdough, rye and pita, and milk and soy "absent" from a pea protein powder. A real Branded whole wheat bread's ingredient statement contains `SOYBEAN AND/OR CANOLA OIL`.

The consequence is intended: the catalog is mostly `UNKNOWN`, and downstream (T-2036) `UNKNOWN` **blocks** the food for a client who declared that allergen. A food excluded on an unanswered question is the correct outcome; a food served on an unverified absence claim is not. Do not "improve" this by inferring absence from a category, a species name or a single-commodity identity.

### Cross-contact invariant
`crossContact` is **always `UNKNOWN`** with `basis: "NONE"`, frozen at the type level. FDC carries no processing or advisory-label facts, and dossier §5.3 forbids converting missing "may contain" text into verified absence.

### `allergenFactsV2` is the only allergen surface on a SOURCED_V2 item
The legacy `allergenFacts` struct has two states — a category is in `contains` or it is not — and its
`verificationStatus` is the literal `"REVIEWED_SOURCE"`, so it **cannot express `UNKNOWN`**. The first real run
produced 1,643 `UNKNOWN` facts against 130 `PRESENT`; projecting that into `contains` stamped all 197 items
"reviewed against the source, contains only these", so `Nuts, almonds` shipped as reviewed and containing
nothing. It fails **open**, and it is the field every pre-existing consumer speaks (review r2 MB-4).

A SOURCED_V2 item therefore carries **no `allergenFacts` at all**, and `foodCatalogContentSchema` rejects one
that does. A consumer that has not been updated gets a compile error and a runtime `TypeError` rather than an
empty array it reads as "no allergens". Read `allergenFactsV2` and treat `UNKNOWN` as exclusion. Catalogs
predating SOURCED_V2 still use `allergenFacts`, which is why the field is optional rather than deleted.

### Allergen token vocabulary
`toLegacyAllergenTokens` projects catalog categories into the **legacy exclusion-token** vocabulary (`lib/ai-coach/catalog/schema.ts` `allergenSchema`, plus `SESAME`), not in the nine-value category vocabulary, via the single translation table `LEGACY_TOKEN_BY_CATEGORY` in `lib/ai-coach/intake-allergens.ts`. A client's declared allergy is projected into that same vocabulary, so `SOYBEAN` → `SOY` and `CRUSTACEAN_SHELLFISH` → `SHELLFISH`. Writing the category name instead would make the first comparison miss, i.e. fail **open** on an allergen. `SESAME` has no legacy catalog value and is projected anyway, because omitting it would make a sesame-containing food look sesame-free; a `SESAME` declaration derives the same token, so the comparison matches and fails closed. A unit test pins the exact string set in both directions. The ingestion no longer writes this projection into the artifact (see above); it is exported for the consumer that has to compare a client's declared token against an `allergenFactsV2` category.

### Handling `OTHER` allergen declarations
T-2002 allows a client to declare `category: "OTHER"` with free-text specificity. **There is deliberately no catalog counterpart for `OTHER`.** Such a declaration resolves to no catalog category and therefore fails closed in T-2036. This is an intentional safety invariant; do not attempt to map `OTHER` into catalog categories.

## 4. Nutrient derivation and energy

- **Which nutrient numbers back a macro.** The accepted values are exported from
  `lib/ai-coach/artifacts/schema.ts` (`SOURCED_V2_ENERGY_NUTRIENT_IDS` and friends) and read by both the mapper
  and the SOURCED_V2 refinement, so the two cannot drift. Energy: `"208"`, `"958"` ("Energy (Atwater Specific
  Factors)"), `"957"` ("Energy (Atwater General Factors)"), searched in that order so a record carrying several
  resolves deterministically; when the figure comes from `"958"`/`"957"` it sets `energyFact.method`, so the
  artifact records which value was used. Fat: `"204"`, `"298"` ("Total fat (NLEA)"). Modern Foundation records
  report the Atwater and NLEA rows instead of the classic ones, and reading only the classic ones made the tool
  refuse 48 records that carry every macronutrient — plain chicken breast, Pacific cod, olive oil, bell
  peppers, walnuts, peanut butter (review r2 MB-1).
- **These are FDC nutrient *numbers*, not nutrient *ids*, and the distinction has already cost one run.** A
  nutrient row carries both: `nutrient.number` is the INFOODS tagname (`"208"`, `"958"`, `"298"`) and
  `nutrient.id` is FDC's own key (`1008`, `2048`, `1085`). `normalizeFdcRecord` reads `number ?? id`, so a real
  response yields the number. The first attempt at the widened lookup was written with ids, matched nothing,
  and refused exactly the same 48 records with exactly the same message. It was invisible to the tests because
  every synthetic Foundation fixture set `number` to the string of its own `id`. The fixtures now keep the two
  apart as USDA does, and a unit test asserts that no fixture may set them equal and that no accepted value is
  an id.
- **Widening the lookup is not deriving a value:** a record that reports no kcal under any accepted number, or
  no fat under any accepted number, is still refused and the run still aborts — see §2.1 for where that
  refusal is recorded.
- **Derivation.** Analytical means *measured*. FDC codes `AS` ("Atwater specific factors") and `AG` ("Atwater general factors") are **calculations** and map to `CALCULATED`; only genuinely analytical codes map to `ANALYTICAL`; an unmapped code maps to `UNKNOWN` with the raw code preserved in `derivationDetail`. The Atwater information lives in `energyFact.method`, which is its right home.
- **Reported zero vs UNKNOWN.** An unreported nutrient is `{ value: null, status: "UNKNOWN" }`. Zero is written only when the record explicitly reports zero.
- **A negative by-difference carbohydrate is a known source artefact, and we exclude rather than clamp.**
  "Carbohydrate, by difference" is 100 minus the other measured components, so it lands slightly below zero
  whenever those sum to a little over 100. Three records in the current allowlist do:
  `2727567 Chicken, thigh, meat and skin, raw` reports `-0.17255`, `2747673 Tuna, ahi or yellowfin, frozen`
  reports `-0.1045`, and `2727569 Chicken, breast, meat and skin, raw` the same. These are genuine USDA
  values, not corruption. Physically they mean "effectively zero", and most nutrition software clamps them.

  We do not. Clamping writes a number USDA did not report — a small instance of the failure this whole ticket
  exists to remove. A negative energy, protein, fat or carbohydrate is a **mapping** error
  (`NEGATIVE_ENERGY` / `NEGATIVE_PROTEIN` / `NEGATIVE_FAT` / `NEGATIVE_CARBOHYDRATE`, and
  `NEGATIVE_NUTRIENT_VALUE` for any other row), so the record flows through the source exclusions channel
  (§2.1) with the real figure in its reason. Zero remains valid; only a strictly negative value is refused.

  **The RD may well decide that a near-zero negative is acceptable to treat as zero, and that is their call to
  make with the number in front of them** — not ours to make silently in the mapper. If they decide it, the
  change is a reviewer-set value, not a clamp in the ingestion code. Coverage cost today is nil:
  `Chicken, breast, boneless, skinless, raw` and four other tuna records map cleanly, so the catalog keeps
  both foods.

  It is a mapping error rather than a schema error deliberately. `nutrients.carbohydrateGrams` and
  `nutrientFacts[].value` are both `nonnegative`, so before this the run aborted at the final
  `foodCatalogContentSchema.parse` after all 245 records had been fetched, with
  `["items",118,"nutrients","carbohydrateGrams"] Too small: expected number to be >=0`. **The final schema
  parse should only ever fail on a bug, never on data.**
- **Macro-energy discrepancy.** `macroEnergyDiscrepancyKcal = reported kcal - (4·protein + 4·carbohydrate + 9·fat)`, recorded as an observation. It is never used to correct a value and never compared to a threshold.

## 5. Test fixtures: synthetic vs recorded

Two directories, and the distinction is structural on purpose:

- **`tests/fixtures/ai-coach/fdc-synthetic/`** — hand-built fixtures that exercise specific code paths. Every file carries a `_synthetic` block naming the path it exercises. They have **no attribution, no licence, no retrieval date and no fdcId in any real range** (they sit above 9,000,000,000). Their key structure mirrors a real `/food/{id}` response so the mapping code is exercised against something representative, but no value in them came from anywhere. They are never evidence of anything about a real food.
**There is no recorded-response directory.** An earlier version of this section documented
`tests/fixtures/ai-coach/fdc-recorded/` "created by the real run" and said the provenance tests bind to it. The
run created no such directory and **no verbatim FoodData Central response is committed anywhere in this repo**,
so the mapping cannot be re-verified against source without a new API key. The promise is removed rather than
left standing; recording a handful of responses is tracked as **T-2017**.

A fixture is one or the other. A hand-built file that carries a provenance claim is the failure this ticket was rewritten to remove.
